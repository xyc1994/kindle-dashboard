# 数据汇聚与更新规则

## 核心决定

运行数据以本机 SQLite `dashboard.db` 为唯一事实源。各数据源可以采用不同脚本、协议和刷新周期，但不得各自维护被渲染器直接读取的 JSON 真相源。

数据库不放在百度同步盘或 Obsidian Vault 内，建议位置：

```text
%LOCALAPPDATA%/KindleDashboard/data/dashboard.db
```

理由：SQLite 是持续写入文件，云盘同步可能产生锁冲突、部分同步或冲突副本。Vault 中只保存 schema、代码、配置模板和项目文档。

## 数据流

```text
Scheduler
  ├─ weather_collector      HTTP / 和风天气
  ├─ obsidian_collector     文件扫描 + 变更监听
  ├─ codex_collector        app-server + 本地降级读取
  └─ device_collector       Kindle 状态回传
             │
             ▼
       统一 CollectorResult
             │
             ▼ 单进程事务写入
        dashboard.db
             │
             ├─> renderer ─> frame.png / frame.svg
             ├─> control API
             └─> 脱敏运行日志
```

所有采集器由一个 Scheduler 调用，数据库只允许该进程写入。渲染器和 HTTP 服务使用只读连接，开启 WAL，并在一个读事务中取得一致性快照。

## 统一对象

采集器输出统一对象：

```yaml
item_id: "source:stable-id"
source: "weather | obsidian | codex | kindle"
kind: "weather | todo | task | quota | intervention | device"
title: "用于显示的主标题"
value: "可选的主要数值"
status: "normal | active | waiting | warning | error | stale"
priority: 0
sort_at: "可选的排序时间"
observed_at: "数据实际观测时间"
expires_at: "数据失效时间"
payload: {}
```

## SQLite 逻辑表

### `items`

当前可显示对象。主键为 `item_id`，包含统一字段和 `payload_json`。每个采集器在单个事务中替换自己的 namespace，失败时不得清空上一次成功数据。

### `source_state`

记录每个来源的：

- 计划周期；
- 上次尝试与上次成功时间；
- 连续失败次数；
- 当前状态与脱敏错误摘要；
- 下次允许运行时间。

### `events`

只保存必要的状态变化，例如“Codex 开始等待授权”“天气恢复”“待办被源文件删除”。按保留期滚动清理，不保存凭据或完整私人正文。

### `ui_state`

保存当前页面、被暂时隐藏的提醒、刷新序号与上次画面 hash。它是本机运行状态，不回写 Obsidian。

## 更新规则

| 数据源 | 正常更新 | 触发更新 | 失效阈值 | 失败处理 |
|---|---:|---|---:|---|
| 和风天气 | 每 2 小时 | 服务启动后立即 | 6 小时 | 保留旧值并标记 stale；10/30/60 分钟有限重试 |
| Obsidian 正式 Memo | 文件变化后 2 秒防抖 | 服务启动、每 15 分钟校验扫描 | 30 分钟 | 保留上次索引并显示来源异常 |
| 日记 `#kindle` 任务 | 同上 | 同上 | 30 分钟 | 同上 |
| Codex 任务状态 | app-server 通知；降级轮询 15 秒 | 线程状态改变 | 1 分钟 | 切换本地数据库降级读取 |
| Codex 额度 | app-server 通知；降级轮询 5 分钟 | 账户额度更新 | 15 分钟 | 保留旧值并显示更新时间 |
| Kindle 电量/充电 | Kindle 每 5 分钟回传 | 启动、充电状态变化 | 15 分钟 | 标记设备状态未知 |
| 页面渲染 | 数据 hash 变化时 | 每分钟时钟刷新 | 不适用 | 保留上一张可用 PNG |

## 和风天气

- 地点：上海市黄浦区。
- v1 初始请求坐标：纬度 `31.22`、经度 `121.49`；首次联调时通过 GeoAPI/响应元数据再次确认。
- 兼容 LocationID 候选：`101020400`，仅作位置核对；v1 天气接口优先使用经纬度。
- 当前天气：`/weather/v1/current/{latitude}/{longitude}`。
- 三日预报：`/weather/v1/daily/{latitude}/{longitude}?days=3&localTime=true&lang=zh`。
- API Host 必须从和风天气控制台配置，不在代码中假定公共固定 Host。
- 认证通过请求头；凭据从环境变量或 Windows 凭据管理器读取。
- 页面底部保留“天气数据：和风天气”归属说明，并处理响应中的 attribution。

每次天气更新包含两次请求：当前天气和三日预报。正常情况下共约 `24` 次请求/日。

## Obsidian 读取与写回边界

第一阶段只读：

- 结构化 Memo 读取 frontmatter 的 `task_id/title/status/due_date/priority/domain/updated_at`。
- 日记只读取带 `#kindle` 的 `- [ ]`。
- 保存相对 Vault 路径、行号与内容 hash，便于未来精确定位。

第二阶段写回必须满足：

1. 操作请求先进入本机命令队列；
2. 写回前重新读取源文件并核对 hash；
3. 文件已变化则拒绝写回并提示冲突；
4. 使用精确 patch 和原子替换；
5. 写后重新读取验证目标 checkbox 或 frontmatter；
6. 不批量修改、不按 mtime 覆盖百度同步冲突副本。

## Codex 介入状态映射

| Codex 状态 | 统一状态 | Kindle 表现 |
|---|---|---|
| `active` | active | 执行中 |
| `waitingOnApproval` | warning | 等待授权，置顶 |
| `waitingOnUserInput` | waiting | 等待回复，置顶 |
| `systemError` / turn failed | error | 任务异常，置顶 |
| `idle` | normal | 完成或空闲 |
| `notLoaded` | normal | 默认不进入首页 |

## 安全与局域网

- HTTP 服务仅绑定可信局域网接口，不暴露公网。
- Kindle 请求携带随机设备令牌；令牌不写入项目 Markdown。
- 操作接口使用固定白名单，不接收 shell、SQL 或任意文件路径。
- 日志不得记录 API Key、JWT、Codex 账户标识或完整私人任务正文。
